## Accessibility baseline findings

### Existing strengths
- root documents declare `lang="en"`;
- primary pages use `main`, headings and native controls;
- most form controls have native labels and/or accessible names;
- error surfaces on several later screens already use `role="alert"`;
- data-heavy surfaces generally use native lists, definition lists or tables;
- current Playwright journeys already exercise role/label based selectors, giving a useful semantic regression base.

### Open gaps
- no dedicated accessibility test script or CI job;
- no pinned accessibility scanner;
- loading/validation state announcements are inconsistent;
- some early pages do not expose asynchronous validation/loading state through live status semantics;
- no explicit keyboard-only/focus-order acceptance suite;
- no explicit zoom/reflow or contrast acceptance evidence;
- table/header semantics and dense trace pages require dedicated review;
- no shared focus/interaction styling contract is present in the inspected app structure.

## API/security baseline findings

### Existing strengths
- synthetic-only startup boundary is fail-fast;
- live-provider activation is fail-fast;
- API host is local-loopback by default;
- CORS origins are configured rather than wildcarded;
- multiple mutating endpoints already use Fastify JSON schemas with `additionalProperties:false`;
- domain/database invariants provide defence in depth for factual immutability and scenario restrictions.

### Open gaps
- no explicit security-header middleware or equivalent API header contract;
- no explicit request-body size in the Fastify constructor;
- no rate-limit control;
- no access-control guard on `/admin/*` API routes;
- browser CORS policy does not itself constitute server-side authorisation;
- generic 500 handling currently includes the thrown error message in the response, which can disclose internal implementation detail;
- schema coverage is not uniform across all mutating endpoints;
- no dedicated negative/abuse-case security suite;
- no explicit CI dependency-vulnerability evidence step.

## Browser security baseline findings

- no `next.config.*` security-header configuration was present in either customer or admin web app;
- no explicit CSP, frame-ancestor, referrer-policy, permissions-policy or nosniff contract is present at the app layer;
- public client environment values currently observed are local API/admin URLs only;
- no real IdP/session or provider credentials are present in the inspected web-app configuration.

## Test/CI baseline

Existing target-stack Playwright proves functional customer/admin journeys but does not yet certify:

- browser/API security headers;
- hostile Origin handling;
- oversized/malformed request handling;
- admin access control;
- internal error redaction.
